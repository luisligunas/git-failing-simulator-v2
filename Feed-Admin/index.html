Hustle Feed: the admin side

Three screens in the Enterprise shell: the ordered list of everything in the Feed, the editor that builds one item, and the targeting modal it opens. Only the first two are new. The targeting modal is the Banner editor’s, reused as it stands. Colours, type and chrome are the app’s own: Hanken Grotesk, the --dark sidebar, --brand-green actions. It should read as a screen the team already has rather than a new design language. The companion Feed mockup specifies what each field does on the phone.

1 · Feed items

Everything in the Feed, in the order hustlers see it. There is no sort control: the order on this screen is the order hustlers get, so sorting it by anything else would show a list you cannot drag. Reordering borrows from the run list: drag the handle, plus anchor on every row. There is no edit-order mode, because ordering is what this screen is for. An anchored item keeps its place above newly created ones instead of being pushed down, which is what a standing Notice or a season banner needs. The order here is the order the server sends, and the app never re-sorts. The list is paged on the server at ten rows, using v-data-table-server’s own footer, the one the withdrawal and submission tables already use: items per page, a range readout, and first, back, forward and last. Page sizes are 10, 25, 50 and 100, matching the three screens that set them explicitly. The # column keeps counting across pages, so the row numbered 11 really is eleventh in the Feed. Searching or changing the status filter goes back to page one. A row can only be dragged among the rows on the page it is on; to move an item a long way, anchor it or change its schedule rather than dragging it page by page. Status is read, never set. Live means the schedule has started, no end has passed and Is Active is ticked. Unticking Is Active overrides everything else and pulls an item immediately without touching its dates, so a cancelled raffle never needs its schedule rewritten to make it disappear.

2 · The item editor

One form for all nine elements. The type picker on the left decides which fields exist; the phone on the right renders the real thing as it is typed, so nobody has to imagine what a colour pair will look like. Delivery (schedule, targeting, active) is the same panel whatever the type. Position is not here: ordering belongs to the list, where you can see what an item sits between. Targeting is the Banner editor’s own targetingType radio group: Edit appears only for Custom Targeting. Both dates are optional and clearable: no Starts means it goes live on publish, no Ends means it runs until removed. Unticking Is Active hides an item straight away and leaves its dates untouched. Neither can be in the past, and Ends must be after Starts. Note the preview byline reads 1 Oct 2026 rather than today, because the timestamp counts from the schedule start.

Editing a collection item

Items are edited one at a time in a modal, the way the Target Selection and Hustler List modals already work. Six fields, all of them the item’s own. The Collection’s orientation decides the image ratio — 5:3 horizontal, 1:1 vertical — which means switching orientation invalidates every existing item image. That is a real failure, not a warning: the images are the wrong shape and the card cannot be saved until they are replaced.

3 · Targeting

Not a new screen. The editor above shows the four targeting states live: All needs no further fields, Run gives a read-only field with a Choose button, Mission is typed straight in, and Custom Targeting reveals the Edit button that opens the modal below. That modal is the one the Banner editor already uses: 720×800, nested ALL/ANY boxes, the same thirteen attributes. The Feed passes its value in and reads the result back; nothing about it changes.

4 · Empty and error states

The list has three states beyond the populated one, and two of them look empty for different reasons: nothing has been created yet, or the search and status filter have excluded everything. The first offers New item, the second offers Clear filters, because telling someone to create an item when they have forty of them behind a filter is worse than saying nothing. Field errors use the form’s own display-errors output: a red border on the input and the message underneath in fg-danger, which is how the Banner form already reports a missing name or an end date that lands before the start. Card images are the one upload with a required ratio, so a mismatch is rejected and the image has to be replaced — including the bulk case, where flipping a Collection’s orientation leaves every existing item the wrong shape at once. Post photos are never rejected and never warned about: the app crops or fits them on its own.

What this reuses

Almost none of this is new surface area. The Banner editor already has Schedule with a start and end, Targeting as All / Run / Mission / Custom, and a redirection field. The Feed editor is the same shape, with a component catalogue in front of it and a live preview beside it.

Already exists
Schedule: start and end dates, from BannerCreateView.
Targeting: All / Run / Mission / Custom, the same screen, not a copy of it.
Hustler groups: the existing module backs “In a hustler group”.
Destinations: the run and mission pickers the banner redirect already uses.
New for the Feed
Type picker: nine elements behind one form.
Live phone preview: the only way colour pickers are usable.
Ordering: drag in the list, since banners have no order to keep.
Is Active: pull an item without editing its dates.
